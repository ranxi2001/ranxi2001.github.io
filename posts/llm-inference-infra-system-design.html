推理 Infra：从计算特征推导系统架构

理解推理基础设施，最容易走的路是先记住一串组件名称：推理引擎、GPU 调度器、模型网关、分布式缓存。问题是，名称能够说明系统用了什么，却不能解释为什么需要它，更不能说明什么时候不该用它。

更可靠的起点是计算本身：一次请求如何消耗算力和显存，请求之间哪些工作可以复用，哪些步骤必须串行，用户又愿意等待多久。沿着这些约束向外推导，引擎负责高效执行，资源层负责提供合适的执行环境，网关负责把请求送到合适的位置，缓存与网络则连接这些局部决策。架构不是组件清单，而是约束条件下的分工。

一、计算特征决定优化问题

本文以常见的 decoder-only、自回归 Transformer 文本生成为主要对象，不将结论直接推广到所有多模态、混合架构或非自回归模型。

首先要分清两组容易混淆的术语。Encoder 与 decoder 是模型结构概念，prefill 与 decode 是推理执行阶段，二者并不对应。 一个没有 encoder 的 decoder-only 模型，同样会经历 prefill 和 decode。

Prefill 处理输入 token，在因果注意力约束下并行计算多个位置的表示，建立后续生成需要的状态，并得到用于生成首个输出 token 的结果。输入较长时，矩阵运算规模通常较大，更有机会发挥 GPU 的并行计算能力。Decode 则在已有上下文基础上逐步生成后续 token；同一条序列的新一步依赖上一步结果，无法像已知输入那样一次性并行展开。

因此，decode 并不是“轻到可以忽略”。每一步仍需执行模型前向计算，读取权重和历史状态，并追加新状态。小批量时，权重读取和内存带宽往往形成限制；上下文增长后，读取 KV 的成本也会上升。具体瓶颈还受模型结构、批大小、并行方式和硬件影响，不能把两个阶段机械地贴成纯计算密集与纯访存密集。

flowchart LR
    A["输入 token 序列"] --> B["Prefill：处理已知上下文"]
    B --> C["建立历史 KV 状态"]
    B --> D["采样首个输出 token"]
    C --> E["Decode：执行下一步前向计算"]
    D --> E
    E --> F["追加新 KV 并采样下一个 token"]
    F --> G{"达到停止条件？"}
    G -->|否| E
    G -->|是| H["结束并释放请求占用"]

这里还必须区分两种复用。基础 KV Cache 是同一请求内的历史复用：缓存先前 token 在各层产生的 key 和 value，避免每次生成都重新计算完整历史对应的 KV。它不意味着整个注意力计算被缓存，新的 query 仍需与可见历史交互。

Prefix Cache 则是跨请求的前缀复用：新的请求若具有兼容的 token 前缀，可以复用已有前缀的 KV，减少对应的 prefill 工作。基础 KV Cache 并不要求有第二个请求，也不要求两个用户提交相同提示词。把两者混为一谈，会直接误导缓存命中率和路由策略的设计。

二、推理引擎：把计算变成受控的执行

有了模型和 GPU，还缺少一层把模型计算转化为高效执行的系统。vLLM、SGLang、TensorRT-LLM 等推理引擎所在的层次，处理的是算子、显存、批次和请求生命周期之间的协调，而不只是封装一个生成接口。

FlashAttention 通过分块和减少中间结果在不同存储层之间的读写，改善注意力计算的访存效率。它不是消除注意力计算，也不意味着所有序列长度都获得相同收益。PagedAttention 的关键是以块管理 KV 的存储与访问，降低连续分配带来的浪费，便于动态扩展和共享。分页机制并不会自动提供跨节点缓存服务，块的所有权、引用计数和回收仍需引擎管理。

Continuous batching 则让批次随执行过程变化：已完成的请求退出，新请求在调度边界加入，而不是等待整批中最长的请求结束。它提高了填充计算资源的机会，但也引入公平性问题。一个长输入的 prefill，可能干扰正在输出的 decode；大量长输出请求，又可能长期占据 KV 空间。

这也是分块 prefill、每轮 token 预算、最大活动序列数和抢占策略存在的原因。分块可以控制单次 prefill 对 decode 的干扰，却可能增加调度开销或改变首字延迟。抢占能够缓解显存压力，但恢复时可能需要重算或搬运状态。参数没有脱离负载的最优值，必须同时观察等待时间和执行时间。

模型侧优化也应放在正确边界内。微调主要改变模型能力与行为，不会直接把模型参数规模缩小；蒸馏才可能通过训练较小学生模型承接特定任务。量化使用更低精度表示，既可能是整数，也可能是低精度浮点，并不保证加速。内核支持、反量化开销、批大小和硬件决定实际效果。剪枝同样需要稀疏执行支持，不能只看被删除的参数。任何优化都应在质量评估通过后，再讨论延迟、吞吐和成本。

三、资源调度：让算力真正成为服务能力

引擎解决的是已经获得资源之后如何执行；资源层解决的是哪些实例可以获得资源、放在哪里、何时增加或回收。两者分别对应计算效率与分配效率，却共享同一个服务目标。

在 Kubernetes 中，GPU 资源声明能够约束 Pod 的放置，但一个 GPU 数量并不足以描述推理容量。还需考虑显存、型号、互联拓扑、驱动与运行时兼容性，以及模型需要的并行配置。异构设备承载同一模型时，也不能只按副本数平均分流，应依据负载下的服务能力分配请求。

如果模型需要多卡协同，相关进程必须获得匹配的资源与通信环境。跨节点并行还会引入网络依赖；跨数据中心则通常应以相对独立的服务池组织，在流量层处理地域选择与故障切换，而不是默认把所有设备拼成一个低延迟计算域。Kubernetes 提供编排基础，但不会自动完成多集群容灾或模型级调度。

弹性也不是修改副本数就完成了。新实例需要经过资源等待、镜像获取、权重读取、加载和预热，才能承担流量。镜像缓存、权重本地副本和分发优化减少的是不同阶段的耗时，应分别计量。Readiness 应表达模型已可服务，而不只是进程存在；缩容则应先停止接收新请求，再排空活动流，避免中断生成。

因此，不能只用 GPU 利用率驱动扩缩容。高利用率可能意味着合理批处理，也可能意味着队列失控、重复计算或大量即将超时的工作。更合理的反馈包括排队时长、待处理 token 量、KV 压力以及 SLO 达标情况，同时保留冷启动余量和扩缩容滞回，避免资源与流量来回振荡。

四、流量网关：感知计算，不接管业务

传统轮询并非没有价值，它是很好的基线。但请求代价不同、缓存分布不同之后，“每个实例收到相同数量的请求”就不再等价于负载均衡。短问短答和长文生成可能只各占一个连接，却消耗完全不同的计算与显存预算。

推理路由需要知道模型版本、租户配额、输入长度、输出预算、截止时间，以及实例队列和缓存线索。这些是计算与服务契约，不是业务语义。支付规则、检索策略、提示词编排和工具调用流程应留在应用层；应用可以声明经过鉴权的优先级与预算，网关不应靠理解提示词内容来决定某个业务是否重要。

分层也有助于控制复杂度：外层处理通用认证、入口防护和服务路由，平台内部处理模型实例选择、推理准入与状态亲和。缓存索引和遥测汇聚可以成为独立模块，避免每个请求都遍历全部引擎。控制面负责配置和期望状态，在线数据面只做有界、可降级的决策。

流式响应还要求网关正确传递取消、截止时间和背压。客户端已经收到部分输出后，不能像普通幂等查询一样透明重试，否则可能出现重复片段或不一致内容。重试应区分尚未输出与已经输出，并依靠请求标识与明确的协议约定控制重复执行。取消如果没有传到引擎，连接虽然关闭，GPU 仍可能继续做无用计算。

五、缓存协同：命中只是决策输入

Prefix Cache 的前提不是“文字看起来相同”，更不是语义相似。必须匹配同一模型权重版本，以及会影响计算的配置，例如适配器、位置编码条件和注意力语义；输入还需经过一致的 tokenizer 与模板处理，形成相同的有效 token 前缀。多模态输入及其编码结果也必须纳入兼容性判断。前缀后面的 token，即使局部文字一样，也不能脱离之前的上下文任意复用。

工程上，缓存键需要包含这些身份与版本信息。共享通常受块粒度约束，命中块数不能直接当作完整请求命中。网关缓存索引可能已经过时，最终是否可复用应由引擎验证；状态不兼容时必须安全回退，不能为提高命中率接受错误结果。

多租户环境还要隔离缓存命名空间、授权访问与淘汰预算。未经授权不能跨租户复用敏感前缀，日志也不应直接记录原始提示词。即使使用哈希索引，也不能忽略存在性和时延侧信道。公开公共前缀若要共享，应有显式策略，而不是把“内容相同”视为访问许可。

真正的路由问题可以用一个假设场景说明：实例 A 已有共享文档前缀，但队列很长；实例 B 空闲，却没有缓存。此时有三条路：等待 A、把 KV 搬到 B、让 B 重算前缀。第一条节省计算但增加排队，第二条消耗传输与导入资源，第三条花费计算但可能更快开始。

flowchart TD
    A["请求与候选实例"] --> B["筛选模型兼容性、租户权限和资源容量"]
    B --> C["估计队列、前缀复用与传输代价"]
    C --> D{"选择满足 SLO 的较低代价路径"}
    D --> E["在缓存所在实例等待并执行"]
    D --> F["迁移兼容 KV 到另一实例"]
    D --> G["在可用实例重算前缀"]
    F --> H{"状态导入是否成功？"}
    H -->|是| I["使用已验证状态继续执行"]
    H -->|否| J["按剩余预算重算或返回失败"]
    E --> K["记录实际延迟与资源消耗"]
    G --> K
    I --> K
    J --> K

比较对象应是预计的端到端收益，而不是孤立的命中率。迁移成本包含数据定位、排队、传输、布局转换和目标显存分配，不能只拿理论带宽估算。缓存下沉到主机内存或 SSD 扩大了容量，却也增加了恢复延迟，只有未来复用价值足够高时才值得保留。

热点进一步改变答案。公共前缀可能吸引大量请求到同一实例，形成“缓存越热，排队越长”的反馈。可以允许热门前缀在多个实例上形成副本，设置亲和性权重上限，或在排队超过阈值时退回负载优先。长短请求的隔离则可通过服务等级、token 预算和独立队列实现；输出长度通常只能估计，不能假装网关能提前准确知道。

六、PD 分离：把干扰转换为传输与协调

Prefill 与 decode 的执行特征不同，因此可以考虑分离资源池，使两阶段独立配置硬件、批处理和容量。它可能减轻长 prefill 对持续生成的干扰，但不是免费优化，也不是所有服务的默认终点。

分离后，decode 端需要获得 prefill 建立的 KV 和必要请求状态。网络、缓存格式、并行布局与接收端显存因此进入关键路径。高带宽设备只是条件之一，还要看拓扑、拥塞、传输实现，以及通信能否与计算重叠。

sequenceDiagram
    participant R as 推理路由与协调层
    participant P as Prefill 池
    participant D as Decode 池
    R->>P: 提交输入与请求标识
    P->>P: 处理前缀并建立 KV
    R->>D: 选择目标并申请接收容量
    D-->>R: 返回可接收状态
    R->>P: 提供传输目标
    P->>D: 传输兼容 KV 与生成状态
    D-->>R: 确认状态可用
    D->>D: 执行后续生成
    D-->>R: 持续返回输出
    R->>P: 按生命周期协议释放暂存状态

图中是逻辑过程，不规定每个实现的通信顺序；首个 token 的采样和返回位置也可以因引擎协议而异。关键是接收确认、失败回收与取消传播必须有定义，不能让两端都以为对方持有可用状态。

PD 分离还要求两类容量联动。只扩 prefill 而 decode 已经饱和，会把瓶颈变成中间状态堆积；只按总 QPS 配比，又会忽略输入与输出长度分布。低并发、短上下文、网络较弱或资源池较小时，共置部署可能更简单且更快。正确问题不是是否足够先进，而是隔离收益能否覆盖搬运、碎片化和运维成本。

七、从 Go 与 Kubernetes 出发的最小实验

验证这套推导，不必一开始就搭建分布式 KV 存储。最小路径是固定模型、引擎版本、精度和生成配置，先建立单实例基线，再引入两个独立副本与一个薄 Go 网关。以下是测试设计，不包含实测性能结论。

Go 网关先实现流式转发、取消传播、超时、有限队列和轮询；使用 Kubernetes EndpointSlice 发现已就绪实例，并通过最小权限的只读访问维护本地快照。服务端健康检查与端点状态共同决定候选集。第二阶段再加入在途请求、排队信息和前缀亲和策略，状态缺失时回退到基线，避免先把策略写成复杂调度平台。

若引擎没有可用的缓存事件接口，可以用前缀哈希亲和作为近似策略，但必须标为“路由提示”，不能声称知道真实缓存位置。只有引擎提供命中 token 或块的统计，才能核验复用。没有两份真实 GPU 容量时，可用模拟后端测试发现、流式协议和故障处理；模拟结果不能证明 GPU 加速或生产容量。

测试输入至少覆盖无共享前缀、可复用公共前缀、热点集中、长短输入输出混合，以及两个租户使用相同文本的隔离场景。分别运行冷缓存和预热状态，固定请求集合并记录实际输入输出 token 数。按到达速率逐级增加负载，保留开放式到达测试，避免客户端等响应再发请求而隐藏系统排队。

指标口径应在实验前固定：

  • TTFT：客户端发出请求到收到首个有效输出 token 的时间，包含网络、网关、排队与首阶段执行，而不把空事件当作首字。
  • TPOT：对输出 token 数大于一的请求，以首个到最后一个 token 的耗时除以后续 token 数；单 token 请求不参与该均值。另记录相邻 token 间隔，避免平均值掩盖停顿。
  • P95：同一测试窗口、同一指标样本的第九十五百分位。分别报告请求级 TTFT、TPOT 与总时延，并按长短请求和租户分组，不能只给一个含义不明的“P95 延迟”。
  • SLO goodput：单位时间内，成功完成且同时满足预先约定 TTFT、TPOT 等约束的请求数。同步报告总吞吐、拒绝、失败和超时比例，防止只统计成功样本美化表现。

流式网络块不一定与 token 一一对应，精确 token 时间需要引擎埋点或协议支持；只能测块到达时，应明确报告测量边界。GPU 利用率、显存占用、排队时间、缓存命中 token 比例和传输字节数则用于解释结果，而不能替代用户侧 SLO。

观测链路最好使用统一请求标识串起网关、引擎与缓存事件，但不要把请求标识或前缀哈希直接作为指标标签，以免制造高基数。跨节点阶段耗时应注意时钟偏差，优先使用各组件本地持续时间并结合追踪事件解释。成本比较也要包含空闲预留、缓存内存与网络开销，不能只比较完成请求时的 GPU 时间。

实验一次只改变一个主要因素：轮询对比负载感知，再对比加入缓存亲和；相同预算下比较共置与 PD 分离。重复测试并记录窗口、样本量、预热方法和版本配置。最后注入 Pod 退出、缓存淘汰、状态延迟、客户端取消等故障，检查路由回退、资源回收和流式错误是否符合约定。任何收益结论都应限定在这些硬件、负载与测量条件内。

结语

推理 Infra 的核心不是让某一层指标最好看，而是让系统在质量、延迟、吞吐和成本之间形成可解释的取舍。引擎可以降低一次执行的代价，资源调度可以缩短容量缺口，网关可以减少错误的请求放置，缓存与 PD 分离则把计算问题进一步变成状态和网络问题。

沿着“计算特征—执行机制—资源供给—请求路由—跨层协同”建立因果链，才能知道一次优化究竟解决了什么、又把成本转移到了哪里。最终需要最大化的不是 GPU 忙碌时间或缓存命中率，而是在既定资源预算下真正满足服务承诺的有效产出。
