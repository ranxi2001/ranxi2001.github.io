Agent 走向生产：从任务完成到证据闭环

一个 Agent 能读懂文本、调用工具并输出结构化结果，只说明一条执行路径已经跑通。生产系统面对的却是持续变化的输入、相互矛盾的证据、不稳定的外部服务，以及会被下游继续使用的判断。一次输出看起来完整，不代表它值得接受；一次任务显示成功，也不代表中途的失败得到正确处理。

从 Demo 走向生产，关键不是把流程画得更复杂，而是把“完成了什么”转化为“凭什么接受这个结果”。业务语义规定什么算正确，执行约束限制错误传播，可观测性保存判断经过，评估与反馈检验修改是否有效。这些环节连接起来，才构成证据闭环。

下文以风险事件抽取案例展开：系统从互联网文本与视频线索中识别事件，提取时间、地点、风险类型，并关联工商主体。文中的企业名称、视频口播、查询故障和版本对照均为教学模拟，用于解释机制，不代表实际测量结果。

一、先定义业务完成，而不是字段填满

假设输入是：“9 月 1 日，位于乙市的某设备有限公司暂停生产，原因尚不明确。”抽取出日期、城市和停产描述并不难，难点在于每个字段的含义及其证据边界。

“暂停生产”不能自动扩展为企业倒闭，“原因不明”不能由模型补成经营困难。“9 月 1 日”若没有可用年份，不能随意生成完整日期。页面发布时间、采集时间与事件发生时间也不是同一概念：它们可以帮助解释相对时间，却不能在缺少依据时相互替代。一个可信结果应保留原始表述、可确定的要素和仍然缺失的信息，而不是用格式完整掩盖事实不足。

主体关联尤其容易制造隐蔽错误。另一段模拟文本提到：“去年刚进去时在甲市培训，年后才调到乙市”，随后说“我们厂里一直叫星禾，工牌上写的是 XH”。仅按简称查询工商库，可能命中不同地区的候选。上下文中的乙市可以帮助缩小范围，但它首先是推断出的工作地点，不是已经核实的注册地址。

因此，同名工商记录不等于同一主体，事件地点也不等于注册地址。培训地点、工作地点、厂区所在地和注册地可能分别指向不同位置。若将推断出的乙市直接作为不可放宽的注册地过滤条件，甚至可能排除真正的候选。查询参数应保留地点的角色和确定程度；候选返回后，仍需寻找原文线索与注册主体之间的关联依据。

业务输出可以分开表达事件事实与工商确认状态。即使企业尚未确认，文本中的简称和停产线索仍然有价值；反过来，查到一家真实存在的企业，也不能证明事件与它有关。允许“部分完成且缺口明确”，比强迫模型填满所有字段更接近真实业务。

二、拆分 Agent，是为了隔离调查而非增加角色

最初的抽取 Agent 可以直接调用工商查询工具。遇到跨段地点时，改进查询依据就可能足够，并不必然需要增加一个 Agent。架构变化应来自任务和上下文的变化，而不是工具数量。

当原文只留下团队线索，例如“星旅项目组让程序员先别来，什么时候恢复也没说”，工商确认便需要探索。教学模拟中的搜索可能命中一张招聘页，其中写着“星旅研发岗位｜乙市”，并列出远帆软件有限公司。这个页面提供了新的企业候选，却仍不能自动证明该公司就是原文团队对应的风险主体：招聘发布者、用人主体、外包服务商可能具有不同角色。

调查需要反复搜索、查看页面、比较候选、核验关系。如果全部放进主 Context，原文与事件要素会和大量搜索片段共享上下文。将工商确认拆为独立 Context 的 subagent，可以把中间调查材料留在局部任务内，让主 Agent 接收结论和必要依据。

flowchart TD
    A["主 Agent：保留原文与事件要素"] --> B["委派：名称、地点角色、原文依据与确认目标"]
    B --> C["工商 subagent：独立调查 Context"]
    C --> D["搜索与工商查询"]
    D --> E["检查候选关系、证据缺口与预算"]
    E -->|"仍有缺口且预算允许"| C
    E -->|"可交付或达到停止条件"| F["返回状态、主体标识、依据或未确认原因"]
    F --> G["主 Agent：合并事件结果并保留证据引用"]

隔离并非没有代价。委派增加调用和交接成本；过度压缩的任务输入可能丢失地点转移、说话者身份或否定语句，摘要也可能把候选误写成结论。因此，任务接口不仅要传递关键词，还要传递相关原文、来源标识和待解决的问题。交付时要区分已确认主体、候选线索与未确认原因，证据引用应能回到保留的调查材料。

如果调查很短且高度依赖主任务的完整语境，保持单 Agent 可能更合适。是否拆分，应比较任务独立性、上下文干扰和交接损失；“多 Agent 更先进”不能替代这一判断。

三、Agent as a Tool：把昂贵能力变成按需服务

视频进一步暴露了资源约束。为每条视频全量解析，可能让成本和延迟先于业务价值增长。更合理的路径是先处理标题与描述，再判断是否存在影响结论的事实缺口。

模拟标题“安成夜班又停了”，只能提供有限线索。若按需读取口播，得到“我们乙市二厂这边，昨晚又没开夜班……白班还在上”，结果就必须收窄为特定厂区和班次，而不是整家企业停产。“昨晚”的绝对时间及工商全称仍需核验。读取失败时，应保留这些缺口，不能把“没有读到”解释为“视频没有说明”。

内容获取可以由独立 Agent 完成：内部选择浏览器操作、视频获取与解析工具，检查结果并决定是否继续；外部则暴露为一次工具调用。这就是 Agent as a Tool：调用方使用稳定的任务接口，但被调用能力内部仍有 Agent Loop，并不只是固定步骤的函数。

事件抽取 Agent、工商 subagent 与上层问答 Agent 都可以复用这个入口，每次调用使用独立 Context，返回与任务有关的内容、来源和缺口。它与 subagent 分工关注点不同：前者强调调用接口和能力复用，后者强调任务委派与上下文边界，两者可以同时成立。

作为工程扩展，这类工具还应约定超时、调用预算、结果大小和访问权限。网页内容应作为待核验材料，而不是能够改写任务目标的指令。共享能力越通用，越需要明确的输入输出契约，否则复杂性只是从主 Agent 转移到了一个不透明的工具内部。

四、前置分类节省成本，也会制造不可见的漏筛

事件解析只是整条数据链路的一环。页面、文本和视频线索先经过清洗、来源去重与相关性分类，再进入深度处理，随后用于事件聚合、风险分级和上层检索问答。若主体在解析阶段误绑，下游可能把多条事件聚到错误企业名下；若前置阶段漏筛，Agent 则根本没有纠正机会。

前置分类可以采用 BERT 或小语言模型，也可以使用 DSPy 优化分类程序。这里真正重要的不是组件名，而是职责分配：低成本步骤缩小处理范围，昂贵的推理与工具调用留给相关或待判断内容。同时通过队列、优先级、并发限制和单任务配额控制执行容量。

flowchart TD
    A["来源接入：保留原文与时间元数据"] --> B["清洗去重与相关性分类"]
    B -->|"相关或待判断"| C["队列调度：优先级、并发与配额"]
    C --> D["Agent 深度处理：按需搜索或读取视频"]
    D --> E["结果接受检查与持久化"]
    B -->|"暂不深度处理"| F["保留来源与筛选决定"]
    F --> G["随机抽检与难例复核"]
    G --> H["识别漏筛并形成评估样本"]
    H --> I["验证分类策略后更新版本"]
    I -.-> B

只在进入 Agent 的样本上评估，会把分类漏筛排除在分母之外，得到过于乐观的端到端结论。因此，筛除数据也要抽检，并保留当时的模型版本、分类结果与来源。普通随机样本用于理解流量分布，难例加采样用于发现边界；两者混合后的错误比例不能不加区分地当成总体错误率。

成本优化也不应只看模型调用费用。排队时间、外部工具耗时、重试、人工复核和错误传播都属于系统代价。减少深度调用是否值得，需要同时检查相关事件召回与下游质量，而不是用调用量下降直接宣布优化成功。

五、错误控制：先诚实表达失败，再讨论恢复

工商查询超时后，系统尚不知道是否存在匹配记录。这与查询成功但候选列表为空，是两种不同事实。工具协议应明确区分 status: error 与成功空结果，并保留错误类型；业务层还应分别记录执行状态和主体确认状态，不能用一个笼统的“成功”覆盖全部含义。

一个典型的教学模拟是：工具已经返回超时，后续模型也确实收到了错误，却仍输出“星禾制造有限公司，已确认”，同时没有工商记录。这说明错误不一定来自工具封装，也可能发生在模型解释错误之后。此时先检查实际输入输出，比直接归因于模型能力不足更可靠。

恢复应由运行时约束，而不是让 Agent 无限尝试。临时网络错误可以在次数、总时长和配额范围内退避重试；权限错误或无效参数需要其他处理；带副作用的操作则必须先明确重试语义。预算耗尽后，系统可以保留已有事件信息，以主体未确认交付或转入复核，但不能凭名称和记忆补全企业。

确定性接受门禁与语义 Eval 必须分工。 程序可以检查确认结果是否包含工商记录、引用是否指向真实保存的材料、字段与状态是否一致；这些是不满足就不能接受的必要条件。但是，一段招聘页即便存在且可访问，也未必支持原文团队与企业之间的关系。证据是否真正支持结论，需要按业务准则进行语义评估。

因此，门禁不能被包装成“真实性证明”。它负责拦截可确定的违规，语义 Eval 负责检验主体、角色、时间和事件范围是否判断正确。门禁拒绝的原因也要进入 Trace，避免系统只留下一个无法解释的失败标签。

六、提交超时：幂等必须约束 K 与 R

结果通过检查之后，仍可能在写入时出错。假设执行器提交结构化事件，存储服务已经写入，但成功响应丢失。调用方看到超时，无法据此判断“未写入”。如果重新运行 Agent、生成另一份结果再直接提交，就可能重复新增或制造相互矛盾的记录。

正确的边界是一次逻辑提交。执行器在提交前保存提交标识 K 与结果 R；超时恢复时复用同一个 K 和同一个 R，而不是重新生成内容。存储服务通过唯一约束识别提交，并将幂等记录与业务结果放在同一事务中提交。

flowchart TD
    A["执行器持久保存待提交的 K 与 R"] --> B["存储服务：开启事务并按 K 检查或占位"]
    B -->|"首次提交"| C["写业务结果与幂等记录：受 K 唯一约束"]
    C --> D["同一事务提交，保存首次凭据"]
    B -->|"K 已存在且请求 R 相同"| E["复用已提交结果与首次凭据"]
    B -->|"K 已存在但请求 R 不同"| F["返回冲突：不覆盖、不新增"]
    D --> G["返回首次提交凭据"]
    E --> G
    G -->|"响应丢失，执行器等待超时"| H["重试完全相同的 K 与 R"]
    H --> B

实现时，查重不能只是“先查再写”的应用层约定，并发请求仍可能同时认为记录不存在。唯一约束负责竞争裁决，冲突后的请求应等待或重新读取已提交记录，再核对请求内容。事务失败则一起回滚，不能留下“幂等记录存在、业务结果缺失”的半完成状态。

R 的比较还需要稳定规则，例如比较规范化后的提交内容，避免序列化字段顺序造成伪差异。同 K、不同 R 必须报冲突，不能静默覆盖。新的业务修订应走明确的版本或更新协议。这套机制防止同一提交重试造成重复写入，并不自动解决不同提交标识指向同一现实事件的业务去重，也不能据此宣称全链路实现了恰好一次执行。

七、Test、Trace、Eval 各自回答一种问题

Test 验证约定行为：注入查询超时后，错误状态是否保留；无工商记录的确认结果是否被门禁拒绝；模拟写入成功但响应丢失后，相同 K、R 的重试是否只产生一份业务结果。这些问题有明确预期，适合单元测试、集成测试和故障注入。

Trace 还原一次执行：主任务派发了什么，子任务实际收到哪些原文，工具使用哪些参数，返回了错误还是空结果，后续模型又输出了什么。它需要关联模型调用、工具调用、父子关系、耗时和状态。任务最终结束不意味着每个子调用都正常，只有展开轨迹才能看见错误是否被后续输出掩盖。

Trace 支持根因假设，却不是效果证明。看到错误进入 Context 后仍被无视，可以提出“明确确认依据并增加接受检查”的修改假设；但不能凭这一条轨迹断定更换模型一定有效，也不能证明该改动不会伤害正常样本。

Eval 则在代表性任务上重新运行系统，检查业务表现与修改代价。主体确认准确率的分母是系统已确认的主体数；确认召回率的分母应是按现有证据本应能够确认的主体数。只减少确认，可能同时减少误绑与召回；一律回答未知不能算完成任务。

还应分别观察时间与事件范围、证据支持、无依据确认、失败状态保留，以及成本和延迟分位数。候选版本即使阻止了超时后的虚构，也要检查证据充分的正例是否仍能确认、相对时间是否被错误补全、视频中的班次边界是否保持。指标必须对应业务错误，而不是汇总成一个无法解释的平均分。

八、从轨迹到 Golden Set，再到持续反馈

生产 Trace 可以成为评估样本的来源，但不能直接成为标准答案。构建 Dataset 时，应随机保留普通任务，定向补充误绑、超时和长尾案例，并补齐证据充分的正例。材料经过去重、脱敏和固化后，保存完整输入、来源时间、工具快照及必要元数据。评子任务时保存它实际收到的输入，评端到端时保存原始任务。

固化工具环境是可比较性的前提。同一名称今天和下周可能查到不同网页；若工具结果同时变化，就难以区分性能差异来自程序修改还是外部环境。原输出可以留下作对照，但参考答案需要另行标注和复核，不能复制 Agent 的回答。

Code、LLM Judge 与人工应共享一套 rubric：评哪项，什么证据足够，什么时候必须保留未确认。代码适合比较标识、状态和确定性约束；Judge 可以判断角色与证据关系，但应输出理由和引用，并用人工标签校准；人工负责歧义、边界与分歧裁决。未经核验的自动标签属于候选或 Silver Set，而不是天然可信的 Golden Set。

Golden Set 的可信性也不等于没有泄漏。应先按事件与来源归组，把转载、近重复和改写放在同一组，再划分开发集、验证集与留出集。开发集用于分析和修改，验证集用于比较候选，但不作为 few-shot 示例；留出集在方案冻结后检查泛化，不参与调参和方案选择。否则，表面上不同的文本可能只是同一事件的复述。

flowchart TD
    A["线上 Trace：普通任务、成功任务与失败任务"] --> B["随机抽样与难例加采样：关联评分"]
    B --> C["人工复核：确定参考答案与失败类型"]
    C --> D["版本化 Dataset：固化工具环境并按事件来源归组"]
    D --> E["开发集修改与验证集候选比较"]
    E --> F["重新运行：生成新 Trace、输出与分场景评分"]
    F -->|"需要修改"| E
    F -->|"方案冻结"| G["独立留出集检查：不用于调参"]
    G -->|"达标"| H["小流量验证、发布与持续观察"]
    H --> A
    H -->|"异常"| I["回退并保存问题证据"]
    I --> C

每次实验都要记录数据、工具、程序、模型、Prompt 和评估器版本；参考答案只交给评估器，不进入被评 Agent 的输入。必要时重复运行观察波动。修好一条失败样例，只能证明该样例改善；代表性评估集、独立留出集与持续线上流量，分别支持更广但仍有边界的结论。

线上通常没有现成答案，可以异步执行约束检查与已校准的 Judge 评分，再人工抽检普通任务和评分分歧。前置筛除数据也必须进入观察范围。复核后的新问题沉淀到版本化数据集，经过离线回归、小流量验证再发布，异常则回退。若某次留出检查暴露的问题被用于后续修改，它就不能继续被视为完全未见的最终证据，需要维护新的独立检验边界。

九、贡献证据，是工程闭环的另一种表达

介绍 Agent 项目时，架构图只能说明系统有什么，不能说明个人做出了什么判断。面试中的项目深度，应由业务约束、备选方案、具体修改与验证材料共同支撑，而不是框架名称或 Agent 数量。

以查询超时案例为例，可以分别说明：依据哪段 Trace 判断错误发生在主体确认阶段；为什么选择加强证据要求与接受门禁；具体修改了哪些接口、Prompt 或执行逻辑；用什么故障测试验证约束；又如何通过完整任务 Eval 检查正常确认能力没有退步。若只完成了模拟测试，就应明确范围，不把预期行为描述成线上收益。

“提出过”“实现过”和“验证过”是不同贡献，最好分别对应决策记录、代码或接口变更、实验配置与结果。质量、成本、延迟以及尚未解决的问题同样属于证据。能解释结论的适用边界，比一句没有样本和版本背景的“效果显著提升”更有说服力。

Agent 走向生产，最终要连接四件事：业务判断能追到依据，执行失败不会悄悄变成成功，修改能够在同一条件下比较，新流量能够修正旧假设。任务完成是一次输出，证据闭环则让系统有能力持续判断：这次为什么可信，下一次怎样做得更好。
